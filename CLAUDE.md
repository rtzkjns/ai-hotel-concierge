## Что мы строим

**Универсальный AI-консьерж для отелей** — бот, который отвечает гостям в мессенджерах 24/7
(WhatsApp, Instagram, Telegram, веб-виджет) на RU/KK/EN/ZH, показывает живые цены/наличие,
помогает бронировать, передаёт сложное живому человеку, ведёт B2B-заявки (группы, MICE).

Это **продукт, а не проект под один отель.** Он работает **поверх любой PMS** (системы управления
отелем), а не заменяет её. **Kazzhol — первый клиент (tenant #1), а не единственный.** Цель —
онбордить на этот же продукт другие отели: каждый новый отель = запись конфига (tenant), а не форк
кода.

Ключевой принцип универсальности: **ядро продукта не зависит от PMS.** Ответы гостям, база знаний,
захват лида, передача человеку, B2B-заявки — не требуют PMS вообще. PMS нужна только для «живого
наличия», и к ней несколько путей (Exely напрямую, iCal, channel-manager хаб, ручной режим) —
PMS это опциональное улучшение, а не пропуск на входе.

## Архитектура (крупными мазками)

- **Движок** `src/core/engine.ts` — оркестрация диалога: собирает системный промпт на отель,
  гоняет цикл инструментов Claude, применяет заслоны (выдуманные цены, род, стиль).
- **Каналы** `src/channels/*` — тонкие адаптеры (whatsapp/instagram/telegram/webwidget): приводят
  входящее сообщение к общему виду и отдают движку. Один движок — много каналов.
- **Провайдеры наличия** `src/integrations/exely/*` — за интерфейсом `AvailabilityProvider`
  (`provider.ts`) и `ReservationClient` (`reservation.ts`). Сейчас: Exely (живой) + Stub (заглушка).
  Дальше добавляются manual/iCal и др. — движок не знает, какой провайдер за интерфейсом.
- **Модель тенанта** `src/tenant/*` — **NEW.** `TenantConfig` (персона, валюта, бренд, языки; далее
  реестр отелей и привязки PMS). `activeTenant` = тенант этого инстанса (сейчас Kazzhol). Один
  инстанс = один тенант; пулинг многих тенантов — позже.
- **Знания** `src/knowledge/*` — статическая база на отель + живая синхронизация Exely Content.
- **Консоль** `src/console/*` — админ-панель для сотрудников (диалоги, заявки, база знаний).
- **Store** `src/store.ts` — SQLite (better-sqlite3). Данные скоупятся по `property` (под-отель).

## Как запускать и тестировать

```bash
npm install
cp .env.example .env      # заполнить ключами (см. OWNER-REQUIREMENTS.md); .env В ГИТ НЕ КОММИТИТСЯ
npm run dev               # локальный запуск (tsx watch)
npm test                  # vitest — 600+ тестов, ДОЛЖНЫ быть зелёными перед любым мержем
npm run typecheck         # tsc --noEmit
```

## Правила работы в этом репо (важно)

1. **НЕ ЛОМАТЬ Kazzhol.** Kazzhol — живой прод. Любой рефактор ядра проверяется тем, что поведение
   Kazzhol остаётся идентичным. Для этого есть golden-тесты (`tests/tenant-golden.test.ts` снимает
   системный промпт байт-в-байт). Перед мержем: `npm test` зелёный + `npm run typecheck` чистый.
2. **Секреты — никогда в гит.** `.env` и `*.db` (там PII гостей + закон КЗ о локализации данных)
   игнорируются. В репо только `.env.example` с пустыми значениями. Не коммить реальные ключи.
3. **Ветки.** `main` — актуальное зелёное состояние. Работа — в фиче-ветках, мерж после зелёных
   тестов. Прод-код исторически = ветка `claude/console-fixes` (деплоился вручную).
4. **Строить универсально.** Новый функционал — через тенант/провайдер-абстракции, не хардкодить
   Kazzhol. Каждый новый отель должен подниматься конфигом, а не правкой кода.

## Текущий фокус

зелёные тесты + Kazzhol байт-в-байт.
