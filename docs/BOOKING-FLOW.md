# Как бот оформляет бронь

Гость называет в переписке даты, номер, имя, телефон и почту → получает ссылку → жмёт одну
кнопку → бронь появляется в системе отеля, а подтверждение приходит ему в тот же чат.

## Почему не через официальный API

Exely Reservation API отвечает 403 на всех трёх кабинетах: в токене пустой список областей
доступа, и Exely отказался его открывать. Поэтому бронь создаётся через внутренний движок
TravelLine — тот же, которым бронирует сайт отеля. Брони от сайтовых неотличимы: тот же
канал продаж, та же нумерация, тот же ваучер.

## Последовательность

Хост `kz-ibe.hopenapi.com` (его называет `RegionMap/host?hotel_code=801`).

1. `POST hotel_availability` — числовой код места (`placements[0].code`). Поиск Exely отдаёт
   места символьно («AdultBed-2»), движок такой код не принимает. Заодно это живая проверка,
   что номер не разобрали, пока гость думал.
2. `POST verify_reservation` с `include_guarantee_options:true` — какие способы оплаты
   допускает тариф. Коды разные у каждого отеля, зашивать нельзя.
3. `POST hotel_reservation_2` с `guarantee:{code,success_url,decline_url}` — создаёт бронь.
4. `GET` по `payment_url` из ответа — переводит её в `confirmed`.
5. `POST read_reservation_2` — читает бронь обратно. Успехом считается ТОЛЬКО статус
   `confirmed` из этого чтения.
6. `GET order_url` (ваучер) — короткий номер Exely, по которому отель ищет бронь.

## Три ловушки, каждая стоила нам фантомных броней

**Поле гарантии в запросе называется `guarantee`.** `guarantee_info` — это имя в ОТВЕТЕ.
Движок молча выбрасывает неизвестные ключи и возвращает настоящий на вид номер брони,
которой фактически нет: `guarantees: []`, статус навсегда `unconfirmed`, до отеля не доходит.

**Шаг 4 обязателен.** Без перехода по `payment_url` бронь остаётся неподтверждённой навсегда.
Проверено контрольным опытом: та же бронь без него через двадцать секунд всё ещё
`unconfirmed`, с ним — `confirmed`.

**Гостю и сотрудникам нужен короткий номер.** Длинный (`20270412-801-1261782749`) в ваучере
подписан «служебный номер» и на ресепшене не находится. Человеческий — шестизначный
(`683759`), он в заголовке ваучера и в теме письма гостю. Exely присваивает его асинхронно,
через минуту-полторы, поэтому он дорешивается фоном и досылается менеджерам.

## Как убедиться, что бронь настоящая

Ответ API с номером — НЕ доказательство, он обманывал дважды. Признаки по убыванию силы:

1. **Остаток номеров в Exely Search падает на единицу.** Это другая система, не та, что
   создаёт бронь. Фантомные брони инвентарь не трогали.
2. **Ваучер `order_url` отдаёт HTTP 200** и показывает шестизначный номер. У несуществующей
   брони — 403.
3. **`read_reservation_2` возвращает `status: "confirmed"`.** Это встроено в код: `place()`
   не может вернуть успех без такого чтения.

## Что бот НЕ умеет

Отменять брони — у движка нет такой точки. Отмена уходит сотрудникам, и гостю бот отмену не
обещает. Это закрыто в коде: `supportsCancel = false`.
