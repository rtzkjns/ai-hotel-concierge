# WhatsApp Cloud API для одного отеля: что реально ОБЯЗАТЕЛЬНО

## 1. Прямой ответ

Для того чтобы ЭТОТ один номер отеля начал отправлять и принимать сообщения через Cloud API при скромном объёме:

| Требование | Обязательно? | Почему |
|---|---|---|
| **Business Verification** (верификация бизнеса) | **Только для масштаба** | Отправлять и принимать можно и без неё; она лишь снимает потолок в 250 исходящих диалогов/24ч и даёт зелёный бейдж. |
| **App Review / Advanced Access** | **Нет** | Требуется только приложениям, которые работают с чужими WABA (BSP). Ваше приложение обслуживает СВОЙ номер → хватает Standard Access. |
| **Tech Provider / Solution Partner статус** | **Нет** | Это статус для тех, кто подключает ДРУГИЕ бизнесы. Отель ведёт один свой номер = «прямой» бизнес, статус не нужен. |

Ваша прошлая команда была права: они не обходили правила — это легальный штатный путь для «прямого» бизнеса.

## 2. Таблица: шаги, что обязательно, что даёт

| Шаг | Обязательно / Опционально | Что открывает | Лимит, если пропустить |
|---|---|---|---|
| Свой Meta Business Portfolio + Developer App с продуктом WhatsApp | **Обязательно** | Доступ к Cloud API вообще | Без него API недоступен |
| Номер зарегистрирован и `status=CONNECTED` на `platform_type=CLOUD_API` | **Обязательно** | Реальная отправка/приём | Сейчас номер `ON_PREMISE / DISCONNECTED` = не работает |
| System User + постоянный токен с `whatsapp_business_messaging` + `whatsapp_business_management` (Standard Access) | **Обязательно** | Аутентификация бота | Без токена нет вызовов API |
| Webhook (callback URL + verify token) с подпиской на поле `messages` | **Обязательно** | **Приём** входящих | Без него бот не получает сообщения гостей |
| Хотя бы один одобренный шаблон | **Обязательно для исходящих-инициатив** | Возможность написать гостю первым | Без шаблона можно только отвечать внутри 24ч-окна |
| Одобрение отображаемого имени (name review) | Обязательно, но это НЕ Business Verification | Показ имени вместо голого номера | Пока на проверке — можно слать, отобразится номер |
| Способ оплаты на WABA | **Обязательно** для платных диалогов | Платные исходящие | Без него платные диалоги не уйдут |
| **Business Verification** | **Опционально** | Потолок 1 000 → 10k → 100k → безлимит, >2 номеров, зелёный бейдж | Потолок **250** бизнес-инициированных диалогов / 24ч |
| **App Review / Advanced Access** | **Опционально (не нужно)** | Работа с ЧУЖИМИ WABA | Не применимо к одному своему номеру |
| **Tech Provider статус** | **Опционально (не нужно)** | Обслуживание других бизнесов | Не применимо |

**Ключевые числа при неверифицированном аккаунте:**
- Входящие от гостей — **без ограничений**.
- Ответы внутри 24-часового сервисного окна (гость написал первым) — **без ограничений**, в счёт не идут.
- Исходящие-инициативы (вы пишете первым по шаблону) — **до 250 уникальных получателей за скользящие 24ч** (с 07.10.2025 лимит считается на уровне всего Portfolio, а не на номер).
- Максимум номеров без верификации — **~2**. Шаблонов — до **250** на WABA.

Для одного отеля 250 новых исходящих диалогов в сутки практически всегда достаточно.

## 3. Минимальный путь «в прод» с наименьшей бюрократией

Реальная проблема — НЕ верификация, а «сантехника»: номер застрял в `platform_type=ON_PREMISE` (мёртвый legacy On-Premises API, финально отключён 23.10.2025), а WABA имеет тип SMB/self-serve (`on_behalf_of type=SELF`), поэтому прямой `POST /register` для него закрыт («Register endpoint is not available for SMB businesses»). Это не стена верификации — это стена типа аккаунта.

**Путь A (рекомендуется для самописного бота с полным контролем `POST /messages` + webhooks) — перенос номера на обычную (не-SMB) WABA:**
1. Создать свой Meta Business Portfolio + Developer App (Business-type) с продуктом WhatsApp.
2. Создать System User и выпустить постоянный токен с `whatsapp_business_messaging` + `whatsapp_business_management` (+ `business_management`), Standard Access — **без App Review**.
3. **Освободить** номер +7 708 709 3000 из SMB-WABA `1363377080731255`: удалить номер (или саму WABA), убедиться, что он снят с On-Premises и 2FA выключена. Он уже `DISCONNECTED`, так что большая часть сделана; возможен короткий cooldown.
4. В App Dashboard → WhatsApp → API Setup «Add phone number», подтвердить владение через OTP (SMS/звонок) на +7 708 709 3000.
5. Задать отображаемое имя (авто-проверка имени, НЕ App Review; можно работать пока «на проверке»).
6. `POST /{new_phone_number_id}/register` с `messaging_product=whatsapp` и 6-значным PIN → `platform_type` станет `CLOUD_API`, `status=CONNECTED`. (Лимит эндпоинта: 10 вызовов на номер / 72ч.)
7. Настроить webhook + подписку на поле `messages` — это включает **приём**.

После этого бот шлёт и принимает. Business Verification, App Review и Tech Provider — просто пропущены.

### ⚠️ Единственный неизбежный ФИЗИЧЕСКИЙ шаг (отделяю от бумажной волокиты)
На **шаге 4** нужно **физически принять OTP-код** на линию +7 708 709 3000 (SMS или звонок). Кто-то должен держать доступ к этому номеру в момент подтверждения. Это не бюрократия — это единственное «железное» действие.

(Альтернатива — Path B, Coexistence, чтобы сохранить приложение WhatsApp Business + историю чатов, — требует, чтобы номер сначала жил в приложении WhatsApp Business, добавляет требование открывать приложение раз в ~13 дней и по факту тянет за собой Tech Provider/BSP-механику с Advanced Access. Для вашей цели самохостинга это добавляет ограничений, а не убирает, поэтому это НЕ минимум.)

## 4. Почему прошлой On-Premise команде требовалось меньше — и доступен ли тот путь сейчас

- **App Review для On-Premises физически не существовал.** On-Prem — это самостоятельно развёрнутый Docker: вы логинились `POST /v1/users/login` логином/паролем контейнера и получали локальный JWT. Не было ни Graph-приложения, ни разрешения `whatsapp_business_messaging` — значит, и подавать на App Review было нечего.
- **Business Verification и там играла роль «только для масштаба»** — номер работал на ограниченном тире без завершённой верификации, как и на Cloud.
- **Что Cloud добавил нового:** только требование Meta-приложения + токена доступа (Meta теперь хостит эндпоинт). Но для «прямого» случая Meta сделала это лёгким через Standard Access — без App Review.

**Доступен ли тот путь сейчас?** Сам подход «прямой бизнес без BV/App Review» — да, доступен и штатен. А вот конкретно **On-Premises API — мёртв** (feature-freeze 09.01.2024, ограничение регистрации 01.07.2024, финальное отключение 23.10.2025). Именно поэтому номер показывает `ON_PREMISE / DISCONNECTED` и ничего не доставляет. Вернуться на старый путь нельзя — нужно перевести номер на Cloud API (Путь A выше), сохранив ту же малую бюрократию.

## 5. Итог: что делать сейчас, а что пропустить

**Делать:**
1. Перевести +7 708 709 3000 на Cloud API по Пути A (освободить из SMB-WABA → добавить и подтвердить OTP на своей обычной WABA → `register` с PIN → webhook на `messages`).
2. Обеспечить доступ к SIM/линии для приёма OTP-кода (единственный физический блокер).
3. Одобрить отображаемое имя и хотя бы один шаблон; привязать способ оплаты.

**Пропустить (не тратить время):**
- ❌ Business Verification — необязательна; лимит 250 исходящих/24ч и без ограничений на входящие и ответы в окне покрывают трафик одного отеля. Сделать позже, только если понадобится >250 новых исходящих в день или для устойчивости аккаунта.
- ❌ App Review / Advanced Access — не нужен для своего номера.
- ❌ Tech Provider / Solution Partner — не нужен, вы не обслуживаете чужие бизнесы.

**Одной фразой:** верификация/App Review/Tech Provider — это не ворота к отправке, а плата за масштаб и за обслуживание чужих номеров; ваша единственная реальная задача — вытащить номер из мёртвого On-Premise/SMB-состояния на `CLOUD_API / CONNECTED`, и это делается без единой из трёх «бумажек».
